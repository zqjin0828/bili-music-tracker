# B站听歌追踪器

一个 Chrome 扩展：自动记录你在 B 站听过多少遍歌，达到阈值后提醒你收藏到「歌」收藏夹。
可选接入 AI（大模型）来提升长尾标题的判定准确率。

**设计文档见 [DESIGN.md](./DESIGN.md) ｜ AI 方案见 [DESIGN-AI.md](./DESIGN-AI.md) ｜ 接入指南见 [AI-SETUP.md](./AI-SETUP.md)**

---

## 它做什么

你在 B 站后台挂着听歌，它默默记录。同一首歌听满 5 次，右下角浮出一张卡片告诉你：
「这首歌你听了几遍了，要不要收藏到『歌』？」

它**不会**代替你点收藏、**不会**调用 B 站接口写你的账号数据、**不会**上传任何东西到服务器。
所有记录都在你自己的浏览器本地。

## 安装（开发者模式加载）

1. 打开 Chrome，地址栏输入 `chrome://extensions/` 回车
2. 右上角打开 **「开发者模式」** 开关
3. 点左上角 **「加载已解压的扩展程序」**
4. 选择本文件夹 `bili-music-tracker`
5. 扩展出现在列表里，图标上会显示当前最高播放次数

> 如果之前装过旧版本，改完代码后回到 `chrome://extensions/` 点扩展卡片上的**刷新图标**，
> 然后刷新 B 站页面（content script 需要重新注入）。

## 使用

### 正常听歌就行

打开任意 B 站视频页，播放。不需要任何操作。

**什么算「听了一次」**（默认值，可在设置里改）：

- 累积有效收听 ≥ `max(30 秒, 视频时长 × 30%)`，**或**
- 听完了 85% 以上

拖着进度条乱拉、只听了 3 秒切走、暂停着不动 —— 都不计数。

### 它怎么判断「这是音乐」

四个信号加权打分（详见 DESIGN.md 第二节），任一环节命中都会记录：
音乐分区（tid）、标题关键词（翻唱/cover/MV/原曲…）、UP 主名字、视频时长区间。

判定不确定的视频会被标为「疑似非音乐」，**默认不计入**。你可以在弹窗里手动「标为音乐」。

### 达到阈值后

右下角弹卡片：

- **「去收藏到『歌』」** —— 自动帮你展开 B 站收藏面板，并把「歌」这个收藏夹高亮出来。
  你只需勾选它、点确定。收藏成功后插件会立刻把这首写进本地索引，**之后不再重复计数**。
- 如果找不到收藏面板（B 站改版了），会**复制歌名到剪贴板**并打开你的收藏夹页，
  你粘贴搜索即可。

> ⚠️ **v1.3.1 修复**：旧版降级跳转用的是 `https://space.bilibili.com/favlist`
> —— 这个地址**缺 mid，实测直接 404「出错啦!」**，所以你会看到「跳过去页面不存在」。
> 现在改为 `https://space.bilibili.com/<你的mid>/favlist`（带 `?fid=` 时直达具体夹），
> 并做了兜底：拿不到 mid 时退回 `https://www.bilibili.com/account/favlist`。

### ★ v1.3：已收藏检测（不再重复计数）

**问题**：旧版只看「听了几遍」，**不知道这首歌是不是已经在「歌」收藏夹里了**。
结果是一首早就收藏过的歌，每次再听都还在累加计数、还会反复弹提醒卡片。

**解决**：扩展现在会维护一份「歌」收藏夹的本地索引（默认每 30 分钟刷新一次），
每次记录播放前先查一遍。命中则：

- **不计数**（视频级、歌曲级都不加）
- **不弹卡片**（直接标为已提醒）
- 右下角给一句轻提示：`这首已在「歌」收藏夹，不再计数 ✓`

判定采用三层，从快到准：

| 层 | 机制 | 特点 |
|---|---|---|
| L1 | 本地索引（`favIndex` / `favIndexes`） | 主力。零延迟、无网络请求 |
| L2 | 页面 DOM 收藏状态 | 兜底。你刚点完收藏、索引还没刷新时也能立刻感知 |
| L3 | 后台定时重建索引 | 每 30 分钟自动同步；**每周再做一次全量重建** |

> **实现细节**：B 站的 `/x/v3/fav/resource/ids?bvid=xxx`（单视频查收藏夹归属）
> 需要 WBI 签名，未签名返回 `{"code":-400}`。而 `/x/v3/fav/resource/list?media_id=xx`
> **不需要签名**，所以本项目改用「拉全量建索引」的方案 —— 「歌」收藏夹 276 条
> 只需 14 个请求，判定时零成本。

**精确匹配收藏夹名**：实测账号下同时存在「歌」和「歌？」两个收藏夹。
索引器会**排除带 `? ？ ! ！` 结尾的干扰项**，精确锁定真正的「歌」；
若真的存在多个同名夹，取内容最多的那个。

**可在弹窗里手动干预**：每条记录都有「标为已收藏 / 取消收藏标记」按钮，
弹窗顶部还显示索引状态（已索引多少首、上次刷新时间）并提供手动刷新按钮。

#### ★ v1.3.1：每周全量重建 + 容量管理 + 自动换夹

**① 索引每周自动重建（两个 alarm）**

| alarm | 周期 | 作用 |
|---|---|---|
| `favIndexRefresh` | 默认 30 分钟 | 常规刷新，索引过期就重建 |
| `favIndexWeekly` | **每 7 天** | 强制全量重建，纠正索引漂移 |

> **为什么需要每周强刷**：索引是「只增不减」的——增量刷新只知道你**加了**什么，
> 如果你在 B 站网页端**手动删了**收藏，插件无从感知，索引会永久偏大，
> 于是那首歌被判成「已收藏」而**再也不计数**。每周全量重建能纠正这种漂移。
>
> ⚠️ 另一个安全设计：**过期索引不参与命中**。索引一旦超过 `favIndexMaxAgeHours`
> （默认 24h），就视为不可信，自动降级到 DOM 判定 + 触发后台刷新 —— 宁可多计一次，
> 也不要因为陈旧数据而永久丢失计数。

**② 收藏夹容量可视化**

点扩展图标，顶部会显示当前收藏夹的容量条：

```
「歌」已索引 276 首 · 3 分钟前
[████░░░░░░░░░░░░░░  ]  容量 276 / 1000 · 还可再收 724 首
每周全量重建 · 上次 2 天前          [新建「歌2」]
```

B 站容量上限（已核实）：

| 收藏夹类型 | 单夹容量上限 |
|---|---|
| **自建收藏夹** | **1000 首** |
| 默认收藏夹 | 50000 首 |

- 到 **90%** 时容量条变黄并提示剩余数量
- 到 **100%** 时变红，提示你去建新夹

**③ 「歌」满了怎么办 —— 自动切换到「歌2」**

不需要改任何设置。机制是**命名约定**：

```
「歌」满了  →  插件自动发现同名溢出夹「歌2」「歌3」…
            →  把它们一并纳入索引（已收藏检测覆盖全部）
            →  收藏目标自动指向第一个没满的夹
```

所以你的操作只有一步：**新建一个叫「歌2」的收藏夹**。之后：

- 已收藏检测会同时查「歌」和「歌2」（在任一夹里都算已收藏，不会重复计数）
- 弹卡片时自动定位到「歌2」
- 容量条会显示整条夹链：`「歌」1000（满）→「歌2」37`

建夹有三种方式：

1. **弹窗里点「新建『歌2』」按钮** —— 插件调接口直接建，建完自动打开新夹
2. 在页面卡片上点「新建『歌2』」 —— 当检测到全满时会主动弹这张引导卡
3. 手动去 B 站「我的收藏 → 新建收藏夹」建一个叫 `歌2` 的，回来点「刷新」即可

> ⚠️ 如果自动建夹失败（未登录 / 收藏夹数量已达上限 / 风控），
> 插件会明确提示失败原因，并引导你手动创建 —— **不会静默失败**。
> 另外「自建收藏夹个数上限」B 站从未公开（社区说法 50/99/100 不一），
> 所以插件只给保守提示，**以页面实际报错为准**。

**④ 溢出夹命名规则**

溢出夹必须满足：`基础名 + 数字`，即 `歌2`、`歌3`……（**不能有空格**）。
带 `? ？ ! ！` 结尾的仍会被排除，所以「歌？」永远不会被误纳入。

### 点扩展图标看统计

- **歌曲榜** —— 按「歌名 + 版本」聚合，跨 UP 主合并同名翻唱
- **视频榜** —— 按 BV 号，每个视频独立计数
- **未达标的会显示进度条**，一眼看出还差几次

每条记录可以：打开原视频、标为音乐、排除、重置提醒、删除。

## 设置项

| 选项 | 默认 | 说明 |
|---|---|---|
| 触发阈值 | 5 | 听几次提醒收藏 |
| 收藏夹名称 | 歌 | 提醒时定位的收藏夹名 |
| 视频级计数 | 开 | 同一 BV 号听几次 |
| 歌曲级计数 | 开 | 同名翻唱跨视频合并 |
| Live/重制并入原曲 | 开 | 周杰伦《晴天》Live 版算进《晴天》原曲。关掉则分开计 |
| 疑似音乐计入 | 关 | 打开后判定不确定的也统计 |
| 静音也计时 | 开 | 关掉则静音时不累计 |
| 最少有效收听 | 30 秒 | 低于这个时长不算一次 |
| 有效收听比例 | 0.3 | 需要听满视频时长的 30% |

### AI 判定（v1.2 新增）

AI 是**可选**的。默认关闭，纯本地规则运行，零成本零延迟。

打开后采用**三层架构**，只有规则引擎拿不准的标题才交给 AI：

```
第 1 层：本地规则（<1ms）  ── 置信度 ≥ 0.85 → 直接采纳，不问 AI
第 2 层：AI 判定（0.5~5s） ── 成功 → 采纳 + 永久缓存
第 3 层：规则结果兜底      ── 任何失败都退回规则，插件永远可用
```

| AI 选项 | 默认 | 说明 |
|---|---|---|
| 判定通道 | 关闭 | `关闭` / `队列中转` / `直连 API` |
| 置信度阈值 | 0.85 | 高于此值不调 AI（省 token 的关键） |
| 永久缓存 | 开 | 每个视频只问一次，之后无限复用 |
| API 端点 / Key / 模型 | — | 仅直连模式需要 |

**两种通道怎么选**

- **队列中转（推荐）** —— 插件**不存 API Key**，更安全。规则拿不准的视频先记进队列，
  由我把队列拿去调 API 再回填。触发方式：在弹窗里点「复制队列」直接粘给我，
  或运行 `node tools/process-queue.js`。
- **直连 API** —— 插件自己调 API，实时生效，无需手动触发。需要在设置里填 Key
  （明文存 `chrome.storage.local`，**建议用权限受限的子 Key**）。

成本和准确率的详细测算见 [DESIGN-AI.md](./DESIGN-AI.md)：配合缓存，一个月重度使用 ≈ **¥0.16**。

**AI 怎么改数**：AI 结果晚于计数到达，所以采用「乐观计数 + 回溯修正」——
先用规则结果记上，AI 回来后如果判定不同，会**扣减或迁移**那一次计数。
比如规则把 `初音ミク` 当成歌名记了一次，AI 纠正为 `千本桜`，计数会从
`初音ミク|original` 迁到 `千本桜|original`。这条链路是**幂等**的，重复导入同一份结果不会重复扣减。

详细接入步骤见 **[AI-SETUP.md](./AI-SETUP.md)**。

### 关于「翻唱版本」的计数口径

- **不同人翻唱同一首歌** → 合并（`千本桜|翻唱`）✅
- **原唱和翻唱** → 分开（`千本桜|original` vs `千本桜|翻唱`）✅
- **Live 版和录音室版** → 默认合并（可在设置里关掉）

## 日语歌支持

日语歌的标题格式跟中文差别很大，v1.1 做了专项适配：

**支持的日语版本标记**

| 日语写法 | 识别为 |
|---|---|
| `歌ってみた` / `弾いてみた` / `カバー` / `演奏してみた` | 翻唱 |
| `オリジナル` / `本家` | 原唱 |
| `ピアノ` / `ギター` / `アコースティック` | 钢琴版 / 吉他版 / Acoustic |
| `カラオケ` / `インスト` / `オフボーカル` | 纯音乐（伴奏） |
| `ライブ` / `生歌` | Live |
| `リミックス` / `アレンジ` | Remix |
| `替え歌` / `パロディ` | 替え歌 |
| `セルフカバー` / `リアレンジ` | Remake |

**实测效果**

```
【初音ミク】千本桜【オリジナル】  → 歌名:千本桜  歌手:初音ミク  版本:原唱
【ピアノ】千本桜                → 歌名:千本桜  歌手:-      版本:钢琴版 ★
YOASOBI「夜に駆ける」           → 歌名:夜に駆ける  歌手:YOASOBI
【MV】King Gnu - 白日          → 歌名:白日    歌手:King Gnu
Neru - 東京テディベア feat.鏡音リン → 歌名:東京テディベア（feat.已剥离）
Aimer - 残響散歌 / THE FIRST TAKE → 歌名:残響散歌（节目名已剥离）
```

★ 这是最关键的修复：早期版本会把 `【ピアノ】千本桜` 当成**原曲**计数，
等于你听 5 次钢琴版，插件以为你在听原曲。

**合辑自动排除**

`【作業用BGM】アニソンメドレー`、`【3時間】作業用 邦楽メドレー` 这类是多首歌的集合，
插件会识别为**合辑**并**跳过歌曲级计数**（仍计入视频级），避免污染歌曲榜。

**不会被误判的标签**

`【MV】【MAD】【フル】【練習】【合唱】【東方】【洋楽】【歌枠】【ED】【OP】` 等
视频格式/出处标签不会被当成歌手名。

## 已知限制

1. **B 站改版会导致选择器失效**。元数据读取有 4 层兜底（`__INITIAL_STATE__` → URL → DOM → playlist），
   但收藏面板的定位依赖 B 站前端结构，改版后可能退化为「复制歌名」模式。
2. **歌名解析不是 100% 准确**。中文标题格式太杂，比如 `起风了 - 买辣椒也用券` 这种
   UP 主名在前的格式无法可靠区分。但 **songKey 不含歌手名**，所以歌手判错不影响合并计数。
3. **不算「我听了几首歌」的平台数据**，它只统计你在这个浏览器里、这个扩展生效期间的行为。
4. 分 P 视频按 `BV号_P页号` 独立计数，适合「一首歌一个 P」的合辑。
5. 日语标题中**同一首歌的假名/汉字写法差异**（如 `千本桜` vs `千本ざくら`）不会自动合并，
   会算作两个 key。中文的简繁差异同理。

## 变更记录

### v1.2.1 — 修复后台播放不计数

**症状**：标签页切到后台（或浏览器最小化）后播放，时长完全不累计，永远达不到计数门槛。

**原因**：累计逻辑用的是**墙钟 tick 间隔**，并丢弃 `> 3000ms` 的间隔：

```js
const delta = now - s.lastTickTs;
if (delta > 0 && delta < 3000) s.accumulatedMs += delta;   // ← 后台时 delta≈60000，被丢弃
```

但 Chrome 会节流隐藏标签页的定时器 —— 隐藏 5 分钟后降到约**每分钟 1 次**。
于是 `delta ≈ 60000` 被当成「异常」丢掉，累计恒为 0。
（隐藏 5 分钟以内是 1 秒节流，还能勉强工作，所以这个 bug 时隐时现。）

**修复**：改用**视频进度推进量**（`currentTime` 增量）累计 —— 视频在后台照常推进，
不受定时器节流影响。再用墙钟推算「正常播放本应推进多少」来区分拖动进度条。

```
后台被节流（wallSec 可能 60s）：ctSec ≈ expected        → 全额计入
拖动进度条：                    ctSec 远大于 expected  → 只计与墙钟相符的部分
```

**同时新增**：
- 左下角**调试面板**（Alt+M 切换），实时显示`累计/需要`秒数、播放状态、判定结果 —— 自己就能验证
- 设置页补了**门槛口径说明**：实际门槛是 `max(最少秒数, 时长×比例)`，
  5 分钟的歌按 0.3 算是需要 **93 秒**，不是 30 秒（这一点之前很容易误解）
- `timeupdate` 采样 + `visibilitychange`/`pagehide` 时主动结算
